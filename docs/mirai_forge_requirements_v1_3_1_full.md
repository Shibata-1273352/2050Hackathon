## 1. プロダクト概要

### 1.1 一文定義

群馬県の2050年「5つのゼロ」を、5つの現在の視点と1つの未来の視点から問い直し、市民協議の出発点をつくるAIです。

### 1.2 アーキテクチャ的位置付け: Civic Reasoning Pipeline

Mirai Forgeは会話AIではなく、公式資料・公開データ・複数の利害視点を、根拠付きで市民協議の問いへと変換する Civic Reasoning Pipeline です。この命名はピッチおよびUIで必ず使用し、「マルチエージェント劇」批判への構造的反論として機能させます。

パイプラインは次のように流れます。公式資料と公開データがRAGに投入され、5つの利害視点による並列推論が走ります。その結果が論点化され、時間反転視座として2050年の市民の手紙が加わります。これによって草案が鍛造され、最終的に市民へ向けた次の問いとして出力されます。

```
公式資料 + 公開データ
        ↓
RAGによる根拠抽出
        ↓
5つの利害視点による並列推論(5 Agents)
        ↓
論点化(Issue Map)
        ↓
時間反転視座(Future Citizen Agent)
        ↓
草案の鍛造(Draft v1 → v2)
        ↓
市民へ向けた次の問い
```

### 1.3 根幹原則

```
AIは合意を決めない。
AIは、合意の出発点をつくる。
決めるのは、市民と行政である。
```

### 1.4 勝ち筋の軸

群馬には2050年の目標があります。しかし、その目標は市民の対話に変換されていません。Mirai Forgeは、5つの現在の声と2050年からの手紙で、最初の問い直しをつくります。

### 1.5 決め台詞

> 未来は予測しない。
> 2050年の声を聞いて、2026年の一歩を変える。

### 1.6 チーム内合言葉(公開しない)

```
手紙で泣かせるな。
手紙で草案を変えろ。
```

すべての実装・演出判断は、最終的に「手紙が草案v2を変えていることが視覚的に証明されているか」で判断します。

## 2. MVP スコープ

### 2.1 入力(1テーマのみ実装)

```
地域: 前橋市
テーマ: 災害時の停電ゼロ
具体的な議論対象: 公共施設を、平時はクールシェア、災害時は電気避難所として使い直す
```

他テーマ(温室効果ガス排出量ゼロ・自然災害死者ゼロ・プラごみゼロ・食品ロスゼロ)はUI上で "Coming Soon" 表示のみとし、実装しません。1テーマに集中することで、デモ密度と実装可能性を両立させます。

### 2.2 出力(4種類)

| # | 出力 | 表示時間 |
|---|---|---|
| 1 | 5体現在エージェントの主張(根拠・仮説ラベル付き) | 約20-25秒 |
| 2 | 論点マップ | 約15秒 |
| 3 | 2050年からの手紙 | 約30秒(クライマックス) |
| 4 | 草案 v1 / 手紙 / 草案 v2 の3カラム比較 + 市民協議の出発点 v0.1 | 約20秒 |

デモ合計は90秒以内に収め、残りはピッチ説明に充てます。

## 3. アーキテクチャ

### 3.1 エージェント構成

| Agent | Phase | Model | Temperature | サブタイトル | 絶対譲らない条件 |
|---|---|---|---|---|---|
| 行政AI | 1 並列 | GPT-4o-mini | 0.2 | 制度・予算・防災計画 | 群馬県既存計画と矛盾する案は支持しない |
| 環境AI | 1 並列 | GPT-4o-mini | 0.3 | 再エネ・脱炭素・レジリエンス | 5ゼロ宣言の数値目標を後退させる案は拒否 |
| 企業AI | 1 並列 | GPT-4o-mini | 0.4 | BCP・採算・地域運営 | 5年以内の黒字化見通しを評価軸とする |
| 生活者AI | 1 並列 | GPT-4o-mini | 0.6 | 高齢者・徒歩圏・避難弱者 | 高齢者徒歩アクセシビリティを優先 |
| 次世代AI | 1 並列 | GPT-4o-mini | 0.9 | 2050年の参加者・長期視点 | 既成概念に挑戦、長期視点を強調 |
| Synthesis Agent | 2, 4 | GPT-4o | 0.5 | — | citation必須、エージェント主張を捏造しない |
| Future Citizen Agent | 3 | GPT-4o | 1.0 | 2050年の前橋市民 | 視座提供のみ。決定権を持たない |

### 3.2 実行フロー(Civic Reasoning Pipeline)

```
入力(地域 × 5ゼロテーマ)
        ↓
RAG Knowledge Base(公式資料・公開データ)
        ↓
Phase 1: 5体並列実行(asyncio.gather)
  → 各エージェントの主張(構造化JSON)
        ↓
       【論点マップ】 ─── UI表示1
        ↓
Phase 2: Synthesis Agent
  → 草案 v1(構造化JSON, summary_label 付き)
        ↓
Phase 3: Future Citizen Agent
  → 2050年からの手紙(構造化JSON, closing_question + short_label 付き)
        ↓
       【手紙】 ─── UI表示2(クライマックス)
        ↓
Phase 4: Synthesis Agent(再実行、手紙を入力に追加)
  → 草案 v2(構造化JSON, summary_label + changes_from_letter 付き)
        ↓
   【3カラム比較 + 協議の出発点 v0.1】 ─── UI表示3
```

### 3.3 Future Citizen Agent — 3世代設計

| 候補 | 2050年 | 2026年時点 | 視点 |
|---|---|---|---|
| 前橋市 田中花子 | 82歳 | 58歳 | 停電・医療・避難の当事者 |
| 前橋市 佐藤蓮 | 24歳 | 0歳 | 2050年生まれ世代の地域参加 |
| 前橋市 小林美咲 | 41歳 | 17歳 | 育つ過程で施策を体験した世代 |

全員を前橋市民で固定することで「なぜ前橋テーマなのに他地域?」という不要な質問を消し、世代差で多様性を確保します。MVPでは田中花子をデフォルト表示とし、3世代切り替えはP1機能としますが、本番デモでは1人に固定します。ピッチでは「複数世代に切替可能」と一言だけ言及します。

### 3.4 安全策(AGENTS.md に必須記載)

実装時にエージェントの設計と実装が要件定義から逸脱しないよう、以下の8項目を AGENTS.md に必須記載します。これらは SHOGUN AI v7.0 で確立済みのパターンを直接転用したもの(1〜7)に、v1.3 で追加した対立生成の構造化(8)を加えたものです。プレゼンには出さず実装で生かします。

```
1. 各エージェントは独立した API call として実行する。
   プロンプト内で他エージェント応答を捏造することは禁止。

2. Synthesis Agent が手紙の内容を予測して先に v2 を生成することは禁止。
   手紙が実際に生成されてから入力として使う。

3. 対立が見つからない場合は「対立を検出できませんでした」と正直に出力する。
   無理やり対立を演出することは禁止。

4. Future Citizen Agent は政策決定を行わない。視座提供のみ。
   全出力は「草案」「議論たたき台」表記。

5. 各エージェント出力は最低1つの根拠ソース表示を必須とする。
   根拠がない主張は「仮説」ラベルを付ける。

6. LLM出力は必ず JSON Schema を経由してUIに渡す。
   structured output を強制する(response_format=json_schema, strict=true)。
   パース失敗時は最大3回再試行し、それでも失敗する場合は cached JSON に
   フォールバックする。これは failure mode として正常に処理されるべき経路。

7. Synthesis Agent は、草案 v2 生成時に必ず changes_from_letter と
   summary_label を出力する。「手紙によって何が変わったか」を明示できなければ、
   その草案は不採用とする。

8. 各現在エージェントの system prompt に「他の視点(行政・環境・企業・生活者・
   次世代のうち自分以外)が言いそうな主張を1つ先取りし、それに対する反駁または
   条件付き同意を claim 内に必ず含めること」を強制する。これにより、temperature
   差(0.2〜0.9)以外に構造的な対立軸を与え、5体の意見が同質化するリスクを
   事前に低減する。実装上は AgentOutput.claim 内に「他視点への応答」要素が
   含まれているかを post-hoc で検証し、欠落していれば再生成する(最大2回)。
   再生成しても満たせない場合は、その issue を IssueMap の open_questions に
   降格させる。これは Section 14 の「Temperature 差で意見が収束する」リスクへの
   事前対策であり、Section 3.1 の「絶対譲らない条件」と組で機能する。
```

## 4. UI/UX 仕様

### 4.1 設計コンセプト

Civic Theater UIをコンセプトとし、チャットアプリにはしません。市民協議を始めるための新しい公共UIとして位置付けます。これは5つのAIが議論する画面ではなく、群馬の2050年目標が市民の問いに変わっていく画面として設計するという思想です。

### 4.2 「問いが鍛えられる」4段階演出

画面体験は次の4段階で「問いが鍛えられる」過程を視覚化します。まず問いが置かれ、次に5つの現在の視点が火花を散らし、続いて2050年の手紙が問いを揺さぶり、最後に市民協議の出発点として鍛え直されます。

### 4.3 1ページ・シネマ型デモ

複数ページ遷移ではなく、1つの大きなステージ画面で進行します。

```
┌────────────────────────────────────┐
│ Header: Mirai Forge / Step Indicator │
├────────────────────────────────────┤
│             Main Stage               │
├────────────────────────────────────┤
│ Bottom: 進行状況・根幹原則・根拠表示 │
└────────────────────────────────────┘
```

Step Indicator: `問いを置く → 入力データ → 現在の声 → 論点マップ → 2050年の手紙 → 協議の出発点`

### 4.4 デザインテーマ

キーワードは「群馬 × 未来 × 鍛造 × 公共性」です。避けるべき方向は、行政ポータル風、ChatGPT風チャット、Web3風グロー、SF都市シミュレーター風、RAG検索UIです。狙うべき方向は、落ち着いた公共性、鍛冶場の熱量、群馬の山並み、2050年から届く静かな緊張感、根拠と仮説が明確な透明性です。

### 4.6 画面構成(7シーン)

#### シーン1: Opening
画面に「未来は予測しない。/ 2050年の声を聞いて、2026年の一歩を変える。」を表示します。背景には抽象化した前橋地図、赤城山稜線、微細な粒子アニメーションを配置し、CTAとして「市民協議を始める」ボタンを置きます。

#### シーン2: Theme Setup
**5テーマカード**(災害時の停電ゼロ / 温室効果ガス排出量ゼロ / 自然災害による死者ゼロ / プラごみゼロ / 食品ロスゼロ)を表示します。MVP で動作するのは「災害時の停電ゼロ」のみで、他4テーマは Coming Soon とします。これにより、群馬県5つのゼロ宣言の全体像と接続しつつ、実装・デモ・審査説明は1テーマに集中する設計です。「問いを始める」ボタンクリックでシーン2.5へ遷移します。

#### シーン2.5: Input Data Reveal
「問いを始める」クリック直後の3-5秒で、入力データを表示します。

```
入力データ
─────────
[公式] 群馬県5つのゼロ宣言
[公式] 群馬県環境基本計画 2021-2030 改訂版
[オープン] 前橋市公共施設一覧
[オープン] 前橋市オープンデータ

これらの根拠から、市民協議の問いを鍛えます
```

設計意図は「ちゃんと地域データに基づいている」ことを審査員に認識させることです。AI出力の信頼性の前提条件として置きます。実装はモーダルではなくフルスクリーンの一時表示で、3-5秒後に自動でシーン3へフェードします。

#### シーン3: Civic Council
中央にForge Core(議論テーマ)を置き、周囲5方向にエージェントカードを配置します。カードの要素はエージェント名、サブタイトル、提案本文(2行以内)、根拠ソースバッジ、仮説ラベルです。信頼度スコアは表示しません。数字が根拠不明だと逆に弱くなるためです。

#### シーン4: Issue Map(UI表示名「論点マップ」)
中央に論点を置き、左に「推進する理由」、右に「議論すべき懸念」を配置します。HTML/CSSの2カラム構成にアイコンと矢印による最低限の構造化を加えます。内部実装名はIssueMapですが、UI表示名は「論点マップ」に統一します。「対立」という言葉は自治体文脈では攻撃的に見える可能性があるためです。

#### シーン5: Letter from 2050
通常カードと質感を完全に差別化します。背景は薄いシアン系グラデーション、紙のような余白、文字間広め、一文ずつフェードイン、最後の問いを中央に大きく強調します。

手紙カード下部には「仮想シナリオ」ラベルを必ず表示します。

```
これは2050年の仮想市民からの手紙です。
未来予測ではなく、現在の協議で見落としうる視点を
明らかにするためのシナリオです。
```

スタイル指針(v1.3.1 改訂)として、フォントサイズは本文の85%、色は公共性 #F8FAFC の80% opacity(従来50%から強化)、配置は **手紙カードの上部・本文の前**、本文フェードイン開始前に1秒先に表示します。これにより、読み手が「これは仮想シナリオである」ことを認識した上で本文に入る流れになります。情緒の強度は本文側のフェードイン演出で担保し、ラベルは倫理的セーフティネットとして本文より早く・はっきりと提示します。

#### シーン6a: 3カラム比較画面 + 変化ラベル

```
┌──────────────┬──────────────┬──────────────┐
│ 手紙の前       │ 2050年の手紙   │ 手紙の後       │
│ Before         │ Letter         │ After          │
├──────────────┼──────────────┼──────────────┤
│ 【変化ラベル】 │ 【変化ラベル】 │ 【変化ラベル】 │
├──────────────┼──────────────┼──────────────┤
│ 草案 v1 詳細   │ 手紙の本文     │ 草案 v2 詳細   │
└──────────────┴──────────────┴──────────────┘
```

実装上の対応は次の通りです。Beforeの変化ラベルは `DraftOutput.summary_label`(v1のsummary_label)、Letterの変化ラベルは `LetterOutput.short_label`、Afterの変化ラベルは `DraftOutput.summary_label`(v2のsummary_label)を使います。中央の手紙カラムは少し大きめ・別質感にして「手紙の重み」を強調します。

この変化ラベル3つがUIで見えることが、Mirai Forgeの最大のクライマックスです。3秒以内に読めるサイズで表示することを必須要件とします。

#### シーン6b: 市民協議の出発点 v0.1

```
タイトル: 市民協議の出発点 v0.1
       前橋市 × 災害時の停電ゼロ

1. 今日の問い
2. 共有できそうな方向
3. まだ議論すべき論点
4. 2050年の手紙で変わった点
5. 根拠
6. 仮説
7. 次に市民へ聞くべき質問
8. 90日アクション
```

見た目は行政資料と市民ワークショップ資料の中間とし、堅すぎず軽すぎず仕上げます。

このシーンの最下部に、共創性を機能として可視化するためのQRコード表示エリアを設けます。「次の市民協議へ」というキャプションとともに、QRコードを表示します。実装上は静的なリンク先を持つQRコード画像で構いません。リンク先は「Mirai Forgeで生成された市民協議の出発点を、実際の市民ワークショップに持っていくための仮想フォーム」を示すページとします。これは v1.2 で追加され v1.3 で P0.5 に格上げされた要素で、「Mirai Forge が市民参加の入り口になる」ことを審査員に視覚的に示すための機能です。

#### シーン7: Closing — 問いで終える

```
Mirai Forge がつくるのは、政策の答えではない。
市民が未来を創るための、最初の問いである。
─────────────────
AIは合意を決めない。
AIは、合意の出発点をつくる。
決めるのは、市民と行政である。
```

最後に決め台詞「未来は予測しない。/ 2050年の声を聞いて、/ 2026年の一歩を変える。」を表示します。

### 6.2 信頼性

API障害時の30秒バックアップ録画(F11)を必須とします。生成中表示でユーザーに進行状況を可視化し、citation不能なら「仮説」ラベルで透明性を担保します。structured output強制によりパース失敗リスクを最小化しますが、失敗時は最大3回まで再試行し、それでも失敗する場合は cached JSON にフォールバックします。全失敗時は30秒バックアップ録画(F11)を表示します。本番デモはcached modeを既定とし、ライブAPI障害の影響をゼロにします。

### 6.3 倫理・安全性

「合意済み」「合意案」「最適解」など、AIが結論を決めたように見える表現を全UIで使いません。ただし「AIは合意を決めない」という根幹原則の説明は例外とします。Future Citizenは決定権を持たないことを明記し、手紙には「仮想シナリオ」ラベルを必ず併記します。全出力に「最終決定は市民・行政が行います」を表示し、個人情報を扱いません(地域単位の集計データのみ)。群馬県既存計画と矛盾する提案には警告ラベルを付けます。

### 6.4 セキュリティ

API keyは環境変数で管理(.env.local)し、LLM APIはバックエンド経由のみとします。フロントエンドへのkey露出は禁止です。デモ動作時のrate limit対策としてキャッシュ層を設けます。

## 8. JSON Schema

### 8.1 設計原則

バックエンドはPydanticで型定義し、フロントエンドはPydanticの `model_json_schema()` で出力したJSON Schemaから TypeScript 型を自動生成します(`json-schema-to-typescript` を採用、`npm run gen:types` で `frontend/lib/types/` 配下に出力)。LLM呼び出しでは `response_format={"type":"json_schema", "json_schema":{...}, "strict":true}` を強制します。これにより、フロントエンドとバックエンドの型整合が保証され、LLM出力のパース失敗リスクが構造的に最小化されます。

### 8.2 AgentOutput

```python
from pydantic import BaseModel
from typing import Literal

class Evidence(BaseModel):
    label: str
    type: Literal["official", "open_data", "hypothesis"]

class AgentOutput(BaseModel):
    agent_id: Literal["admin", "env", "biz", "citizen", "next_gen"]
    agent_name: str
    subtitle: str
    claim_id: str  # 例: "claim_admin_01"。IssueNode.source_claim_ids から参照される
    stance: Literal["推進", "条件付き推進", "懸念", "代替案"]
    claim: str  # 2行以内
    reasons: list[str]
    evidence: list[Evidence]
    hypotheses: list[str]
    concerns: list[str]
```

### 8.3 IssueMapOutput

```python
class IssueNode(BaseModel):
    issue: str
    supporters: list[str]            # agent_id list
    objectors: list[str]
    conditional_supporters: list[str]
    open_questions: list[str]
    source_claim_ids: list[str]      # この論点の根拠となる AgentOutput.claim ID 群
                                     # UI で論点 → 元発言 → 根拠 の trace 用

class IssueMapOutput(BaseModel):
    issues: list[IssueNode]
```

`source_claim_ids` は、論点マップ画面で各 issue を選択した際に、もとになった現在エージェントの主張(AgentOutput)へドリルダウンできるようにするための逆参照です。UI実装上は P1 で良いですが、スキーマ上は MVP から定義しておきます(凍結後の追加はスキーマ変更で破壊的になるため)。

### 8.4 LetterOutput

```python
class LetterOutput(BaseModel):
    citizen_name: str       # 例: "田中花子"
    citizen_age: int        # 例: 82
    citizen_location: str   # 例: "前橋市"
    year: int               # 例: 2050
    paragraphs: list[str]
    closing_question: str   # 例: "誰が、最後まで取り残されるのか?"
    short_label: str        # 3カラム比較の中央ラベル用
                            # 例: "取り残される人は、どこで決まるのか?"
```

### 8.5 DraftOutput

```python
from typing import Literal
from pydantic import BaseModel, model_validator

class DraftOutput(BaseModel):
    version: Literal["v1", "v2"]
    summary_label: str               # 3カラム比較の見出し用(1行)
    question: str
    shared_direction: str
    discussion_points: list[str]
    changes_from_letter: list[str]   # v1: 必ず [] で出力 / v2: 非空必須
    evidence: list[str]
    hypotheses: list[str]
    citizen_questions: list[str]
    actions_90days: list[str]

    @model_validator(mode="after")
    def _validate_changes_from_letter(self):
        if self.version == "v1" and self.changes_from_letter:
            raise ValueError("v1 では changes_from_letter を空配列にしてください")
        if self.version == "v2" and not self.changes_from_letter:
            raise ValueError("v2 では changes_from_letter を必ず1件以上出力してください")
        return self
```

`DraftOutput` は v1 / v2 共通の単一スキーマとします。OpenAI strict schema との互換性を保つため、`changes_from_letter` は v1 でも必須フィールドとして出力させ、v1 では空配列 `[]` とします(LLM プロンプトで明示出力を強制)。`version == "v2"` の場合のみ validator で `changes_from_letter` が非空であることを要求し、満たさない場合は §3.4 安全策 #7 に従い再生成します。`summary_label` はLLMに1行で生成させます。長くなったら再生成します。

### 9.2 OpenAI 主軸の選定根拠

`response_format=json_schema, strict=true` の安定性が公式ドキュメントで明示されています。過去の開発実績による再利用コストが低く、Agents SDKとの親和性も高いです。5体並列実行時の per-token cost が GPT-4o-mini で十分に低く抑えられます。

| 用途 | モデル |
|---|---|
| 5体現在エージェント | GPT-4o-mini(速度・コスト優先) |
| Synthesis Agent | GPT-4o(合議統合に高品質が必要) |
| Future Citizen Agent | GPT-4o(情緒性と具体性が必要) |
| 本番デモ | cached JSON 既定 |
| ライブ生成 | デモ拡張・Q&A時のみ使用 |
| Anthropic Claude | バックアップ・cached生成時の品質比較 |

ハッカソンでは「動かない凝ったUI」より「確実に動く美しいUI」が勝つという前提に基づき、ライブ生成は補助機能として位置付けます。

### 12.0 構成方針(v1.3 で改訂): Before/After 先出し型

### 13.7 このシナリオの勝ち筋と、審査員の疑問への防御線

このシナリオが優勝を狙える理由は6つあります。第一に、手紙が単なるポエムでないことが視覚的に明白で、「効率最大化」から「孤立する人を起点」への変化が3カラム変化ラベルで一目でわかります。第二に、群馬・前橋の地域文脈に深く根付いており、公民館・薬局・寺院など生活感のある具体性を持っています。第三に、AI必然性が出ており、5視点の並列処理と時間反転視座、そして構造化された協議の出発点は人間の会議では時間がかかりすぎます。第四に、共創性が出ており、「次に市民へ聞くべき質問」が具体的で、市民参加への接続が CivicHandoffQR とともに明白です。第五に、倫理的に安全で、AIは決定を下さず「協議の出発点」を出力するのみであり、手紙には「仮想シナリオ」ラベルを併記します。第六に、記憶に残る具体性として「1.2km」「2031年8月の3日連続停電」「毎朝顔を合わせていた商店」など、審査員の脳裏に残る固有名詞・数字を含んでいます。

ただし、上記の勝ち筋は審査員が疑問を抱かないという前提では成立しません。v1.3 では、想定される審査員の疑問4つに対する防御線を明示します。

| 想定される疑問 | 防御線 |
|---|---|
| (a) cached 演出疑念 — 「これは AI が推論したのではなく、事前に作り込んだストーリーではないか?」 | Section 12.3 想定問答に明示。同 JSON Schema を live でも実行できる設計を強調。Q&A時に ?mode=live で単一エージェントの live 実演オプションを準備 |
| (b) 死亡描写の倫理性 — 「弱者の死を情緒で動員しているのではないか?」 | Section 13.5 で3カラム表示語を「徒歩圏から外れた一人暮らしの方」に中和。Section 4.6 シーン5 の「仮想シナリオ」ラベルを視認性強化。本文の悲劇描写は情緒の核として残すが、UI上長く残るテキストからは「死」の直接表現を排除 |

### 13.8 CivicHandoffQR 最小仕様(凍結)

CivicHandoffQR は、Mirai Forge が生成した「市民協議の出発点 v0.1」を、実際の市民協議ワークショップに持ち込むための最小導線です。MVP では静的QRコードから仮想フォームへ遷移しますが、フォーム項目・運営主体・責任分界・データ保存方針・撤退時手順は v1.3.1 で以下のように凍結します。これにより「QRが画面に出るだけで実体がない」という共創性軸への批判を構造的に防ぎます。

**フォーム項目(7項目、提出版で固定)**:

1. 対象地区または町名(任意、例: 前橋市内の地区名)
2. 今日の出力で残したい問い(選択式 + 自由記述)
3. 災害時に最後まで開いていてほしい場所(自由記述)
4. 取り残されそうな人・状況として気になった点(自由記述、個人名は書かない旨を注記)
5. 次の市民協議に呼ぶべき相手(選択式: 住民 / 自治会 / 福祉関係者 / 民間拠点 / 行政 / その他)
6. ワークショップ参加希望(任意、Yes/No)
7. 連絡先(任意。参加希望者のみ。氏名 + メールアドレスまたは電話番号)

**運営主体**:

CivicHandoffQR の運営主体は **コード・フォー・グンマ(Code for Gunma)** とします(主催者であり、本要件 §1 表に明示)。人工知能学会は発表・後援文脈での接続先であり、フォーム運営責任は負いません。日本通信株式会社および株式会社 CATENAS は協賛・地域DX文脈での関心接続先で、フォーム個人情報へはアクセスしません。CATENAS 側で参加ログ化・合意形成支援基盤への接続を将来検討する場合は、Code for Gunma との別途協議を経るものとします。

**責任分界**:

Mirai Forge 自体は政策決定・避難所指定・民間拠点との契約を行いません。出力およびフォーム回答は、市民協議の論点整理に使う参考情報です。最終判断は市民・行政・関係団体の協議に委ねます。フォーム回答に具体的な個人名・医療情報・要支援者の住所などが含まれた場合、集計利用せず削除または匿名化します。これは §6.3 倫理・安全性の延長として CivicHandoffQR にも明示適用される条項です。

**データ保存方針**:

MVP デモ時は実個人情報の収集を必須としません(本選デモは仮想フォーム遷移のみ)。実ワークショップ試行時に収集するデータは、原則として地区名・自由記述・選択回答のみとし、個人情報は参加希望者の連絡先に限定します。自由記述と選択回答は90日間保管し、集計後に匿名化します。連絡先はワークショップ連絡目的に限り使用し、実施後30日以内、最長180日以内に削除します。データは Code for Gunma 管理下のストレージに保管し、第三者へ共有しません。

**撤退時手順**:

CivicHandoffQR を継続しない場合、Code for Gunma はフォーム受付を停止し、QR 遷移先に「受付終了」を表示します。未処理の連絡先は削除し、自由記述は個人が特定できない形に匿名化した上で、協議メモとして保存または破棄します。協議メモを保存する場合も個人名・連絡先・具体住所は残しません。QR コード画像はデモ資料・スライドから削除または「受付終了」版に差し替えます。

**MVP 提出版の実装範囲**:

5/16 提出時点の実装は、(a) フォーム項目1-7 の HTML 静的フォーム(送信は Google Form または同等の無料サービスで暫定可)、(b) 「受付終了」版ページの準備、(c) Mirai Forge デモ画面 シーン6b 末尾からの QR 画像表示、までとします。データの実運用処理(90日匿名化・撤退時削除)は本選後の実証フェーズに位置付け、本要件では仕様文書として固定するに留めます。

## 16. CLAUDE.md 推奨内容(Plan mode 補助)

実装時の Claude Code セッション用 CLAUDE.md として推奨される内容は次の通りです。

```markdown
# Project: Mirai Forge
群馬2050ハッカソン提出作品。Civic Reasoning Pipeline 設計。
Next.js 14 + Python(FastAPI)+ OpenAI Agents SDK + Tailwind + shadcn/ui

## Team Motto(Internal Only)
手紙で泣かせるな。手紙で草案を変えろ。
すべての判断は「手紙が草案 v2 を変えていることが視覚的に証明されているか」で行う。

## Commands
- `npm run dev`: Next.js 開発サーバー(port 3000)
- `npm run lint`: ESLint + 型チェック
- `npm run build`: プロダクションビルド
- `uvicorn backend.api.routes:app --reload`: バックエンド開発サーバー
- `python -m backend.tests`: バックエンドテスト

## Architecture
- `/backend/agents`: 6体のエージェント(5現在 + 1未来)+ Synthesis
- `/backend/orchestrator`: 4 Phase の Civic Reasoning Pipeline
- `/backend/schemas`: Pydantic 型定義(AgentOutput, IssueMapOutput, LetterOutput, DraftOutput)
- `/backend/rag`: PDF 投入と検索
- `/backend/cache/demo_seed.json`: Section 13 のシナリオを反映した cached JSON
- `/frontend/app`: Next.js App Router
- `/frontend/components`: UI コンポーネント(Civic Theater UI)

## Code Style
- TypeScript strict mode、`any` 禁止
- Python は型ヒント必須、Pydantic ベース
- Tailwind utility classes、カスタムCSS 禁止
- LLM 呼び出しは structured output を強制(strict=true)
- LLM 出力は必ず Pydantic でパースしてからUIに渡す
- パース失敗時は最大3回再試行 → cached JSON フォールバック

## Constraints
- .env ファイルを絶対にコミットしない
- API key はバックエンドのみで参照、フロントエンド露出禁止
- エージェント間でプロンプト内シミュレーションを禁止
 (各エージェントは独立した API call として実行)
- 「合意」表記を全UIで使わない(根幹原則の説明は例外)
- 信頼度スコアを表示しない
- 草案 v2 は必ず changes_from_letter と summary_label を出力する
 (出力できなければ再生成)
- 本番デモは ?mode=cached を既定とする。?mode=live は Q&A 拡張のみ
- 手紙には「仮想シナリオ」ラベルを必ず併記
```

## 17. 競合差別化マップ

30チームの中で勝つには相対評価が必要です。想定される他チーム作品とMirai Forgeの差別化を明示します。

| 想定競合 | 強そうな点 | Mirai Forge の勝ち方 |
|---|---|---|
| 防災AIダッシュボード | 実用性が高い、データ可視化が美しい | 我々は「データを見る」のではなく「未来世代の視点で政策を変える」 |
| 高齢者見守りAIチャットボット | 社会課題が明確、共感を得やすい | 我々は見守るのではなく、行政案そのものを問い直す |
| 観光促進AI / 観光プランナー | デモ映えする、地域経済への接続 | 我々は観光より公共性。審査員の納得感で勝つ |
| エコ家計簿 / カーボンオフセットAI | 個人行動変容、わかりやすい | 我々は個人最適ではなく、地域の合意形成に踏み込む |
| まちづくりチャットボット / Decidim 風 | 作りやすい、参加型 | 我々はチャットではなく「争点→手紙→改訂」の体験で勝つ |
| 他の multi-agent 作品 | 技術的に近い(最大の脅威) | 我々は「2050年からの手紙」+「3カラム変化ラベル」の情緒的UX。Civic Reasoning Pipeline 命名で構造的に差別化 |

### 17.1 最大脅威への対策: もし他チームも multi-agent civic AI を作ったら

他チームが「複数視点で合議する市民参加AI」を作る可能性は低くないため、これが起きた場合の防衛策が必要です。

Mirai Forgeの構造的優位として、「2050年からの手紙」(時間反転視座)は把握する限り国内事例がなく、3カラム変化ラベルによる「手紙が草案を変える」視覚的証明は独自設計であり、Civic Reasoning Pipeline という命名は「マルチエージェント劇」批判への構造的反論となります。

プレゼン上の差別化テクニックとして、「これは会話AIではない」を冒頭で言い切り、「マルチエージェント」という言葉を使わず代わりに Civic Reasoning Pipeline と呼び、手紙を最初に出さず5体の対立から論点マップを経て手紙へと至る順番で「重み」を作ります。

### 17.2 協賛企業文脈への配慮

協賛企業として日本通信株式会社と株式会社CATENASが明示されているため、彼らの関心領域(通信・地域DX・社会実装)に少しだけ寄せることで、審査時の「自分ごと感」を生み出します。ただし、寄せすぎは禁物です。重いインフラ提案に変える必要はなく、田中花子の手紙や草案の中に、生活継続インフラとしての視点を一文だけ追加するのが正解です。本要件のSection 13.3で田中花子の手紙第三段落に「家族と連絡が取れる回線も生きていて」と挿入し、Section 13.4で草案 v2 の discussion_points に「停電時の通信確保(衛星・無線・地域メッシュ)— 生活継続インフラとして」を追加することで、日本通信への配慮を実現しています。

CATENAS への配慮としては、CivicHandoffQR(Section 4.7・F22 で v1.3 から P0.5 に格上げ)と Section 4.6 シーン6b の「次の市民協議へ」導線を、地域DX の参加ログ化・合意形成支援基盤として位置づけ直します。Mirai Forge は「市民協議の出発点を生成する画面」で完結せず、QR 経由で生成結果を実際の市民ワークショップに持ち込む参加経路を一体運用します。これは CATENAS が手がける地域DX・社会実装の文脈と接続し、「画面の中で完結する作品ではなく、地域参加基盤への接続点」というメッセージを審査員に視覚的に示します。協賛企業二者への配慮は対称構造になっており、片寄りの印象を最小化しています。
