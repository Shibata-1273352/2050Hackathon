## 1. プロダクト概要

### 1.1 一文定義

群馬県の2050年「5つのゼロ」を、5つの現在の視点と1つの未来の視点から問い直し、市民協議の出発点をつくるAI。

### 1.2 アーキテクチャ的位置付け: Civic Reasoning Pipeline

Mirai Forge は会話AIではない。**公式資料・公開データ・複数の利害視点を、根拠付きで市民協議の問いへ変換する Civic Reasoning Pipeline** である。この命名はピッチおよび UI で必ず使用する。

```
公式資料 + 公開データ
        ↓
RAG による根拠抽出
        ↓
5つの利害視点による並列推論 (5 Agents)
        ↓
論点化 (Issue Map)
        ↓
時間反転視座 (Future Citizen Agent)
        ↓
草案の鍛造 (Draft v1 → v2)
        ↓
市民へ向けた次の問い
```

### 1.3 根幹原則

```
AIは合意を決めない。
AIは、合意の出発点をつくる。
決めるのは、市民と行政である。
```

### 1.4 勝ち筋の軸

群馬には2050年の目標がある。しかし、その目標は市民の対話に変換されていない。Mirai Forge は、5つの現在の声と2050年からの手紙で、最初の問い直しをつくる。

### 1.5 決め台詞

> 未来は予測しない。
> 2050年の声を聞いて、2026年の一歩を変える。

### 1.6 チーム内合言葉 (公開しない)

```
手紙で泣かせるな。
手紙で草案を変えろ。
```

すべての実装・演出判断は、最終的に「手紙が草案 v2 を変えていることが視覚的に証明されているか」で判断する。

## 3. アーキテクチャ

### 3.1 エージェント構成

| Agent | Phase | Model | Temperature | サブタイトル | 絶対譲らない条件 |
|---|---|---|---|---|---|
| 行政AI | 1 並列 | GPT-4o-mini | 0.2 | 制度・予算・防災計画 | 群馬県既存計画と矛盾する案は支持しない |
| 環境AI | 1 並列 | GPT-4o-mini | 0.3 | 再エネ・脱炭素・レジリエンス | 5ゼロ宣言の数値目標を後退させる案は拒否 |
| 企業AI | 1 並列 | GPT-4o-mini | 0.4 | BCP・採算・地域運営 | 5年以内の黒字化見通しを評価軸とする |
| 生活者AI | 1 並列 | GPT-4o-mini | 0.6 | 高齢者・徒歩圏・避難弱者 | 高齢者徒歩アクセシビリティを優先 |
| 次世代AI | 1 並列 | GPT-4o-mini | 0.9 | 2050年の参加者・長期視点 | 既成概念に挑戦、長期視点を強調 |
| Synthesis Agent | 2, 4 | GPT-4o | 0.5 | — | citation必須、エージェント主張を捏造しない |
| Future Citizen Agent | 3 | GPT-4o | 1.0 | 2050年の前橋市民 | 視座提供のみ。決定権を持たない |

### 3.2 実行フロー (Civic Reasoning Pipeline)

```
入力 (地域 × 5ゼロテーマ)
        ↓
RAG Knowledge Base (公式資料・公開データ)
        ↓
Phase 1: 5体並列実行 (asyncio.gather)
  → 各エージェントの主張 (構造化JSON)
        ↓
       【論点マップ】 ─── UI表示1
        ↓
Phase 2: Synthesis Agent
  → 草案 v1 (構造化JSON, summary_label 付き)
        ↓
Phase 3: Future Citizen Agent
  → 2050年からの手紙 (構造化JSON, closing_question + short_label 付き)
        ↓
       【手紙】 ─── UI表示2 (クライマックス)
        ↓
Phase 4: Synthesis Agent (再実行、手紙を入力に追加)
  → 草案 v2 (構造化JSON, summary_label + changes_from_letter 付き)
        ↓
   【3カラム比較 + 協議の出発点 v0.1】 ─── UI表示3
```

### 3.3 Future Citizen Agent — 3世代設計

| 候補 | 2050年 | 2026年時点 | 視点 |
|---|---|---|---|
| 前橋市 田中花子 | 82歳 | 58歳 | 停電・医療・避難の当事者 |
| 前橋市 佐藤蓮 | 24歳 | 0歳 | 2050年生まれ世代の地域参加 |
| 前橋市 小林美咲 | 41歳 | 17歳 | 育つ過程で施策を体験した世代 |

**全員前橋市民で固定**。世代差で多様性を確保。MVPでは田中花子をデフォルト表示。3世代切り替えは P1 機能だが、本番デモでは1人固定。ピッチで「複数世代に切替可能」と一言だけ言及。

### 3.4 安全策 (AGENTS.md に必須記載)

```
1. 各エージェントは独立した API call として実行する。
   プロンプト内で他エージェント応答を捏造することは禁止。

2. Synthesis Agent が手紙の内容を予測して先に v2 を生成することは禁止。
   手紙が実際に生成されてから入力として使う。

3. 対立が見つからない場合は「対立を検出できませんでした」と正直に出力する。
   無理やり対立を演出することは禁止。

4. Future Citizen Agent は政策決定を行わない。視座提供のみ。
   全出力は「草案」「議論たたき台」表記。

5. 各エージェント出力は最低1つの根拠ソース表示を必須とする。
   根拠がない主張は「仮説」ラベルを付ける。

6. LLM出力は必ず JSON Schema を経由してUIに渡す。
   structured output を強制する (response_format=json_schema, strict=true)。
   パース失敗時は最大3回再試行し、それでも失敗する場合は cached JSON に
   フォールバックする。これは failure mode として正常に処理されるべき経路。

7. Synthesis Agent は、草案 v2 生成時に必ず changes_from_letter と
   summary_label を出力する。「手紙によって何が変わったか」を明示できなければ、
   その草案は不採用とする。
```

## 4. UI/UX 仕様

### 4.1 設計コンセプト

**Civic Theater UI** — チャットアプリにしない。市民協議を始めるための新しい公共UI として位置付ける。

5つのAIが議論する画面ではなく、**群馬の2050年目標が市民の問いに変わっていく画面**として設計する。

### 4.2 「問いが鍛えられる」4段階演出

```
1. 問いが置かれる
2. 5つの現在の視点が火花を散らす
3. 2050年の手紙が問いを揺さぶる
4. 市民協議の出発点として鍛え直される
```

### 4.3 1ページ・シネマ型デモ

```
┌────────────────────────────────────┐
│ Header: Mirai Forge / Step Indicator │
├────────────────────────────────────┤
│             Main Stage               │
├────────────────────────────────────┤
│ Bottom: 進行状況・根幹原則・根拠表示 │
└────────────────────────────────────┘
```

Step Indicator: `問いを置く → 入力データ → 現在の声 → 論点マップ → 2050年の手紙 → 協議の出発点`

### 4.4 デザインテーマ

キーワード: **群馬 × 未来 × 鍛造 × 公共性**

避ける方向: 行政ポータル風 / ChatGPT風チャット / Web3風グロー / SF都市シミュレーター風 / RAG検索UI

狙う方向: 落ち着いた公共性 / 鍛冶場の熱量 / 群馬の山並み / 2050年から届く静かな緊張感 / 根拠と仮説が明確な透明性

スタイル: フォントサイズは本文の70%、色は公共性 #F8FAFC の50% opacity、配置は手紙カードの下部、closing_question の下。フェードインのタイミングは手紙本文が全表示された後。

```

│ Before         │ Letter         │ After          │
```

**重要**: この変化ラベル3つが UI で見えることが、Mirai Forge の最大のクライマックス。**3秒以内に読めるサイズで表示する**ことを必須とする。

### 4.10 UI で守るべきルール

| ルール | 悪い例 | 良い例 |
|---|---|---|
| AIが結論を決めるに見せない | 「最適解を生成する」「合意案」 | 「協議の出発点をつくる」「共有できそうな方向」 |
| シミュレーションに見せすぎない | 「2050年の停電リスクを予測」 | 「公開データで議論の対象地域を具体化」 |
| 根拠と仮説を必ず分ける | 全主張を同じ重みで表示 | 根拠欄と仮説欄を物理的に分離 |
| 信頼度スコアを表示しない | 「確信度 87%」 | バッジ「[公式]」「[仮説]」のみ |
| 会話AI に見せない | 「あなたの質問に回答します」 | 「公式資料から問いを鍛えます」 |
| 手紙を装飾扱いしない | 手紙の後に何も変わらない | 草案 v2 が変化ラベル付きで明示的に変わる |

### P0.5 — 本選で勝つために必須

| ID | 機能 | 受入基準 |

| F19 | Auto Demo Mode (cached を本番の既定とする) | URL パラメータで動作モード切替、3段フェールセーフ機能 |

## 6. 非機能要件

### 6.1 性能

| 項目 | 目標値 |
|---|---|
| 5体並列実行の完了時間 (live mode) | 30秒以内 (per-agent timeout 25秒) |
| Future Citizen 手紙生成 (live mode) | 15秒以内 |
| 草案 v2 生成 (live mode) | 15秒以内 |
| 全体デモ実行時間 (cached mode) | 90秒以内 |

### 6.2 信頼性

- API 障害時の30秒バックアップ録画必須 (F11)
- 生成中表示でユーザーに進行状況可視化
- citation不能なら「仮説」ラベルで透明性を担保
- structured output 強制によりパース失敗リスクを最小化する
  - 失敗時は最大3回まで再試行
  - それでも失敗する場合は cached JSON にフォールバック
  - 全失敗時は 30秒バックアップ録画 (F11) を表示
- 本番デモは cached mode を既定とし、ライブAPI障害の影響をゼロにする

### 6.3 倫理・安全性

- 「合意済み」「合意案」「最適解」など、AIが結論を決めたように見える表現を全UIで使わない (「AIは合意を決めない」という根幹原則の説明は例外)
- Future Citizen は決定権を持たないことを明記
- 手紙には「仮想シナリオ」ラベルを必ず併記
- 全出力に「最終決定は市民・行政が行います」を表示
- 個人情報を扱わない (地域単位の集計データのみ)
- 群馬県既存計画と矛盾する提案には警告ラベル

### 6.4 セキュリティ

- API key は環境変数で管理 (.env.local)
- LLM API はバックエンド経由のみ。フロントエンドへの key 露出禁止
- demo 動作時の rate limit 対策 (キャッシュ層)

## 8. JSON Schema

### 8.1 設計原則

- バックエンド: Pydantic で型定義
- フロントエンド: Pydantic から JSON Schema を出力 → TypeScript 型を自動生成 (datamodel-code-generator)
- LLM 呼び出し: `response_format={"type":"json_schema", "json_schema":{...}, "strict":true}` を強制

### 8.2 AgentOutput

```python
from pydantic import BaseModel
from typing import Literal

class Evidence(BaseModel):
    label: str
    type: Literal["official", "open_data", "hypothesis"]

class AgentOutput(BaseModel):
    agent_id: Literal["admin", "env", "biz", "citizen", "next_gen"]
    agent_name: str
    subtitle: str
    stance: Literal["推進", "条件付き推進", "懸念", "代替案"]
    claim: str  # 2行以内
    reasons: list[str]
    evidence: list[Evidence]
    hypotheses: list[str]
    concerns: list[str]
```

### 8.3 IssueMapOutput

```python
class IssueNode(BaseModel):
    issue: str
    supporters: list[str]            # agent_id list
    objectors: list[str]
    conditional_supporters: list[str]
    open_questions: list[str]

class IssueMapOutput(BaseModel):
    issues: list[IssueNode]
```

### 8.4 LetterOutput

```python
class LetterOutput(BaseModel):
    citizen_name: str       # 例: "田中花子"
    citizen_age: int        # 例: 82
    citizen_location: str   # 例: "前橋市"
    year: int               # 例: 2050
    paragraphs: list[str]
    closing_question: str   # 例: "誰が、最後まで取り残されるのか？"
    short_label: str        # 3カラム比較の中央ラベル用
                            # 例: "取り残される人は、どこで決まるのか？"
```

### 8.5 DraftOutput

```python
class DraftOutput(BaseModel):
    version: str                     # "v1" または "v2"
    summary_label: str               # 3カラム比較の見出し用 (1行)
    question: str
    shared_direction: str
    discussion_points: list[str]
    changes_from_letter: list[str]   # 手紙で変わった点 (v2のみ)
    evidence: list[str]
    hypotheses: list[str]
    citizen_questions: list[str]
    actions_90days: list[str]
```

`summary_label` は LLM に1行で生成させる。長くなったら再生成する。

- Agents SDK との親和性

### 13.7 このシナリオが「勝つ」理由

1. **手紙が単なるポエムでないことが視覚的に明白**: 「効率最大化」→「孤立する人を起点」という変化が3カラム変化ラベルで一目でわかる
2. **群馬・前橋の地域文脈に深く根付いている**: 公民館・薬局・寺院など生活感のある具体性
3. **AI必然性が出る**: 5視点の並列処理 + 時間反転視座 + 構造化された協議の出発点は、人間の会議では時間がかかりすぎる
4. **共創性が出る**: 「次に市民へ聞くべき質問」が具体的で、市民参加への接続が明白
5. **倫理的に安全**: AIは決定を下さず、「協議の出発点」を出力するのみ。手紙には「仮想シナリオ」ラベルを併記
6. **記憶に残る具体性**: 「1.2km」「2031年8月の3日連続停電」「毎朝顔を合わせていた商店」など、審査員の脳裏に残る固有名詞・数字

## 14. リスクと緩和策

| リスク | 影響 | 緩和策 |
|---|---|---|
| 5体が「対立を演じているだけ」と見抜かれる | 致命的 | Temperature差分化 + 絶対譲らない条件の構造設計 + Civic Reasoning Pipeline 命名 |
| 手紙がポエム扱いされる | 致命的 | 3カラム比較 + 変化ラベル3つで「草案を変える機能」として可視化 (チーム合言葉) |
| 手紙の死亡描写への倫理的批判 | 中 | UI上に「仮想シナリオ」ラベルを併記 |
| 2週間で完走できない | 致命的 | Gate 1/2/3 で進捗判定。Gate 2 で判定基準を明文化。縮退時は3体動的+2体固定の Plan B に切替 (UI上は5視点維持) |
| デモ中のAPI障害 | 致命的 | Auto Demo Mode (F19) を本番は cached 既定で使用 |
| 公式テーマ呼応の手抜き感 | 中 | 公式引用は冒頭1回 + 締め前1回に分散。間に自分の解釈を挟む |
| 法的責任 | 中 | 「草案」「議論たたき台」表記で決定支援を明示 |
| メンバーB/C のコミット未確定 | 大 | Day 0 中に確定 |
| RAG投入データが揃わない | 中 | 公式PDF優先。サンプル10件で十分とする |
| エージェント構成が混乱する | 大 | 本要件3.1で固定。次世代AIを絶対に外さない |
| LLM 出力パース失敗 | 大 | structured output 強制 (strict=true) + 3回再試行 + cached JSON フォールバック |
| 共創性が薄いと評価される | 中 | シーン6b の「次に市民へ聞くべき質問」とシーン7のクロージングで補強 |
| 30秒並列実行に間に合わない | 中 | per-agent timeout 25秒。GPT-4o-mini で速度確保 |
| Temperature 差で意見が収束する | 中 | system prompt に role priming を強化。post-hoc に類似度を確認し、必要なら再生成 |

## 16. CLAUDE.md 推奨内容 (Plan mode 補助)

実装時の Claude Code セッション用 CLAUDE.md として推奨される内容:

```markdown
# Project: Mirai Forge
群馬2050ハッカソン提出作品。Civic Reasoning Pipeline 設計。
Next.js 14 + Python (FastAPI) + OpenAI Agents SDK + Tailwind + shadcn/ui

## Team Motto (Internal Only)
手紙で泣かせるな。手紙で草案を変えろ。
すべての判断は「手紙が草案 v2 を変えていることが視覚的に証明されているか」で行う。

## Commands
- `npm run dev`: Next.js 開発サーバー (port 3000)
- `npm run lint`: ESLint + 型チェック
- `npm run build`: プロダクションビルド
- `uvicorn backend.api.routes:app --reload`: バックエンド開発サーバー
- `python -m backend.tests`: バックエンドテスト

## Architecture
- `/backend/agents`: 6体のエージェント (5現在 + 1未来) + Synthesis
- `/backend/orchestrator`: 4 Phase の Civic Reasoning Pipeline
- `/backend/schemas`: Pydantic 型定義 (AgentOutput, IssueMapOutput, LetterOutput, DraftOutput)
- `/backend/rag`: PDF 投入と検索
- `/backend/cache/demo_seed.json`: Section 13 のシナリオを反映した cached JSON
- `/frontend/app`: Next.js App Router
- `/frontend/components`: UI コンポーネント (Civic Theater UI)

## Code Style
- TypeScript strict mode、`any` 禁止
- Python は型ヒント必須、Pydantic ベース
- Tailwind utility classes、カスタムCSS 禁止
- LLM 呼び出しは structured output を強制 (strict=true)
- LLM 出力は必ず Pydantic でパースしてからUIに渡す
- パース失敗時は最大3回再試行 → cached JSON フォールバック

## Constraints
- .env ファイルを絶対にコミットしない
- API key はバックエンドのみで参照、フロントエンド露出禁止
- エージェント間でプロンプト内シミュレーションを禁止
  (各エージェントは独立した API call として実行)
- 「合意」表記を全UIで使わない (根幹原則の説明は例外)
- 信頼度スコアを表示しない
- 草案 v2 は必ず changes_from_letter と summary_label を出力する
  (出力できなければ再生成)
- 本番デモは ?mode=cached を既定とする。?mode=live は Q&A 拡張のみ
- 手紙には「仮想シナリオ」ラベルを必ず併記
```

## 17. 競合差別化マップ

30チームの中で勝つには相対評価が必要。想定される他チーム作品とMirai Forgeの差別化を明示する。

| 想定競合 | 強そうな点 | Mirai Forge の勝ち方 |
|---|---|---|
| 防災AIダッシュボード | 実用性が高い、データ可視化が美しい | 我々は「データを見る」のではなく「未来世代の視点で政策を変える」 |
| 高齢者見守りAIチャットボット | 社会課題が明確、共感を得やすい | 我々は見守るのではなく、行政案そのものを問い直す |
| 観光促進AI / 観光プランナー | デモ映えする、地域経済への接続 | 我々は観光より公共性。審査員の納得感で勝つ |
| エコ家計簿 / カーボンオフセットAI | 個人行動変容、わかりやすい | 我々は個人最適ではなく、地域の合意形成に踏み込む |
| まちづくりチャットボット / Decidim 風 | 作りやすい、参加型 | 我々はチャットではなく「争点→手紙→改訂」の体験で勝つ |
| 他の multi-agent 作品 | 技術的に近い (最大の脅威) | 我々は「2050年からの手紙」+「3カラム変化ラベル」の情緒的UX。Civic Reasoning Pipeline 命名で構造的に差別化 |

### 17.1 最大脅威への対策: もし他チームも multi-agent civic AI を作ったら

**リスク**: 他チームが「複数視点で合議する市民参加AI」を作る可能性は低くないため、これが起きた場合の防衛策が必要。

**Mirai Forge の構造的優位**:
- 「2050年からの手紙」(時間反転視座) は、把握する限り国内事例なし
- 3カラム変化ラベルによる「手紙が草案を変える」視覚的証明は独自設計
- Civic Reasoning Pipeline という命名は、「マルチエージェント劇」批判への構造的反論

**プレゼン上の差別化テクニック**:
- 「これは会話AIではない」を冒頭で言い切る
- 「マルチエージェント」という言葉を使わない (代わりに Civic Reasoning Pipeline)
- 手紙を最初に出さず、5体の対立 → 論点マップ → 手紙の順で「重み」を作る
